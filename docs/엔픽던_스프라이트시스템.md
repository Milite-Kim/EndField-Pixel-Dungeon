# 엔픽던 스프라이트(Sprite) 시스템 설계

> 오퍼레이터 인게임 스프라이트 렌더링 구조 및 네이밍 계층 전략.

---

## 1. 네이밍 계층 전략

엔픽던은 SPD 엔진 위에 얹은 모드다. SPD의 `Hero` 클래스는 플레이어 컨트롤러로서
**387개 파일 / 1,674회** 참조되며, 세이브 직렬화(Bundle 키)·액터 스케줄러·버프·
아이템 전반에 깊게 박혀 있다. 이를 전면 개명(`Hero`→`Operator`)하는 것은
**고위험·고노력·기능변화 0**이며 기존 세이브 호환성까지 깨뜨린다.

따라서 **계층 분리** 전략을 채택한다.

```
┌─ 엔진 계층 (SPD 상속) ───────────────────────┐
│  Hero          ← 플레이어 컨트롤러 (직렬화·스케줄링·액션)  │  당분간 유지
│  HeroSprite    ← 스프라이트 엔진 베이스                  │
└──────────────────────────────────────────────┘
                  ↑ 위에 얹기
┌─ 엔픽던 도메인 계층 (신규/확장) ─────────────┐
│  Operator / activeMainOperator               │  엔픽던 네이밍은 여기서 시작
│  OperatorSprite ← HeroSprite 확장             │
│  OperatorRegistry, ChainQueue, ...           │
└──────────────────────────────────────────────┘
```

**원칙**: 새로 작성하는 엔픽던 전용 코드는 전부 `Operator` 네이밍을 쓴다.
상속받은 SPD 엔진 코어(`Hero`, `HeroSprite`)는 콘텐츠가 안정된 뒤
**별도 전용 리팩토링 태스크**에서 일괄 개명한다 (IDE 리네임 + 세이브 마이그레이션).

## 2. OperatorSprite 구조 (방식 B)

### 왜 HeroSprite를 확장하는가

`Hero.moveSpeed()` 내부에서 `((HeroSprite) sprite).sprint(...)`를 **무조건 캐스팅·호출**한다
(`Hero.java`). 따라서 메인 오퍼레이터의 sprite도 반드시 `HeroSprite`의 하위 타입이어야
`ClassCastException`을 피한다.

→ `OperatorSprite extends HeroSprite`로 두면 `sprint()`, `fly`, `read()`, `avatar()` 등
   기존 HeroSprite 기능을 그대로 상속하면서, 텍스처·프레임 셋업만 오버라이드할 수 있다.

### 핵심 오버라이드: `updateArmor()`

HeroSprite의 `updateArmor()`는 SPD 방어구 티어(12×15 프레임)를 기준으로 애니메이션을
구성한다. 오퍼레이터는 방어구 티어 개념이 없고 **64×64 단일 시트**를 쓰므로
`updateArmor()`를 통째로 오버라이드한다.

```java
@Override
public void updateArmor() {
    Operator op = Dungeon.hero.activeMainOperator;
    String sheet = (op != null) ? op.spriteSheet() : null;
    if (sheet == null) { super.updateArmor(); return; }   // 폴백

    texture(sheet);
    TextureFilm film = new TextureFilm(texture, FRAME_SIZE, FRAME_SIZE); // 64×64

    // 현재는 스탠딩 1프레임 → 모든 애니메이션이 프레임 0 공유
    idle    = new Animation(1,  true);  idle.frames(film, 0);
    run     = new Animation(20, true);  run.frames(film, 0);
    die     = new Animation(8,  false); die.frames(film, 0);
    attack  = new Animation(15, false); attack.frames(film, 0, 0); // 2프레임 → onComplete 콜백 보장
    zap     = attack.clone();
    operate = new Animation(8,  false); operate.frames(film, 0, 0);
    read    = new Animation(8,  false); read.frames(film, 0, 0);   // ★ 누락 시 게임 정지 (2-A 참조)
    fly     = new Animation(1,  true);  fly.frames(film, 0);
}
```

> **철칙 ①  `super`를 타지 않는 오버라이드는 부모의 애니메이션 필드를 *전부* 채운다.**
> 하나라도 비우면 그 액션에서 콜백 체인이 끊긴다. 사유는 2-A 참조.
>
> **철칙 ②  non-looped 애니메이션은 반드시 2프레임 이상.**
> `attack`/`operate`/`read`/`die`는 **마지막 프레임 종료 시점**에 `onComplete()`가 발동한다.
> 1프레임이거나 `looped = true`면 종료 시점이 없어 콜백이 영영 안 불린다.

## 2-A. 사례: `play(null)` 오판으로 인한 게임 전체 정지

> 발생 `21e7fd0` (2026-06-11, OperatorSprite 최초 도입) · 수정 `54eabe6` (2026-09-10)
> 증상: **주문서(스크롤)를 읽으면 게임이 멈춤.** 화면은 계속 그려지고 입력도 받지만
> 턴이 영원히 진행되지 않음. 크래시 로그 없음.

### 무엇이 잘못됐나

도입 당시 이 문서에는 아래와 같은 결론이 적혀 있었다. **틀린 결론이다.**

> ~~`fly`/`read`는 HeroSprite의 `private` 필드라 서브클래스에서 못 채운다.
> 그러나 `MovieClip.play(anim)`은 `if (anim != null)` 가드를 가져 null 재생이 안전하다.
> → HeroSprite 엔진 코드 무수정 달성.~~

`play(null)`이 "안전"한 것은 **예외를 안 던진다**는 뜻일 뿐이다. 실제 동작은:

```java
// MovieClip.play()
curAnim = anim;          // ← null이 그대로 대입된다
...
if (anim != null) { frame(anim.frames[0]); }

// MovieClip.update()
if (curAnim != null) { updateAnimation(); }   // ← 통째로 스킵
```

`curAnim == null`이면 `updateAnimation()`이 아예 돌지 않고,
그 안에서 호출되는 **`animCallback`도 영영 호출되지 않는다.**

### 정지에 이르는 경로

```
Scroll.readAnimation()
  └ curUser.busy()                        // ready = false
  └ ((HeroSprite)curUser.sprite).read()
      └ animCallback = { idle(); ch.onOperateComplete(); }
      └ play(read)   ← read == null  →  curAnim = null
                                      →  updateAnimation() 스킵
                                      →  animCallback 미발동
                                      →  onOperateComplete() 미호출
                                      →  ready()/next() 미호출
```

영웅이 `ready = false`, `curAction = null`, `next()` 미호출 상태로 굳으면
`Actor.current`가 영웅에 물린 채 풀리지 않는다. `GameScene.update()`는
`if (!Actor.processing())` 조건에서만 액터 스레드를 깨우므로 **영구 대기**에 빠진다.
크래시가 아니라 "멈춤"으로 보이는 이유가 이것이다.

### 왜 놓쳤나 — 재발 방지 포인트

1. **`private` 필드는 서브클래스에서 보이지 않아 점검 목록에서 통째로 빠진다.**
   당시 `attack`/`operate`의 2프레임 규칙은 *인지하고 지켰는데*, `read`는
   `private`이라 존재 자체가 시야에서 사라졌다.
   → 부모 클래스의 애니메이션 필드는 **소스를 직접 열어 전수 확인**할 것.
2. **"엔진 코어 무수정"을 목표로 삼은 것 자체가 함정이었다.**
   접근 제어자 하나(`private` → `protected`) 때문에 우회 설계를 택했고,
   그 우회가 조용한 정지를 낳았다. 코어 최소 수정이 정답인 경우가 있다.
3. **조용한 실패가 크래시보다 나쁘다.** 크래시였다면 도입 당일 잡혔을 버그가
   3개월간 잠복했다. 콜백 체인이 걸린 자리에서는 "예외가 안 난다"를
   안전 근거로 쓰지 말 것.

### 수정 내용

- `HeroSprite`: `fly`, `read`를 `private` → `protected`
- `OperatorSprite.updateArmor()`: `read`(2프레임), `fly` 정의 추가

`fly`도 같은 이유로 null이었으나, `jump()`는 `super.jump()`가 이동 완료 콜백을
따로 들고 있어 정지까지는 가지 않고 스프라이트가 마지막 프레임에 잠깐 굳는
정도였다. 그래서 플레이 중 눈에 띄지 않았고 `read`만 하드 프리즈로 드러났다.

### 앞으로 같은 유형이 재발할 수 있는 지점

- SPD 업스트림 머지로 `HeroSprite`/`CharSprite`에 **새 애니메이션 필드가 추가**될 때
  → `OperatorSprite.updateArmor()`도 같이 갱신해야 한다. 안 하면 즉시 동일 증상.
- `MobSprite` 계열을 파생시켜 `updateArmor()`류를 `super` 없이 오버라이드할 때
- 모션 시트 제작 후 프레임 인덱스를 교체할 때
  → 실수로 1프레임짜리 `attack`/`operate`/`read`를 만들면 철칙 ②에 걸린다.

## 2-B. 벽 오버행 가림 회피 (skipCells)

### 문제

`DungeonWallsTilemap`은 **"남쪽 칸이 벽/문이면 그 칸에 오버행을 그리는"** 방식이고,
`GameScene`에서 `walls`가 `mobs`보다 **나중에** 추가되어 위에 그려진다.

| 상황 | 결과 | 판정 |
|------|------|------|
| 캐릭터 **남쪽**에 벽 | 그 벽의 오버행이 캐릭터 칸에 그려져 **하단부가 가려짐** | ✅ 의도된 깊이 표현 — 유지해야 함 |
| 캐릭터 **북쪽**에 벽 | 16px 스프라이트는 위로 안 뻗어 문제없음 | ✅ |

그러나 오퍼레이터 스프라이트는 **64×64(4타일)** 이라 머리가 북쪽 칸까지 뻗어,
**뒤에 있어야 할 북쪽 벽에 머리가 잘린다.**

### 해법

레이어 순서를 뒤집으면(=히어로를 walls 위로) 남쪽 벽의 하단 가림까지 잃는다.
따라서 SPD가 자체 대형 스프라이트(`CrystalSpireSprite` / `FungalCoreSprite`)에 쓰는 방식 그대로,
**머리가 침범하는 북쪽 칸의 벽 렌더링만 선택적으로 생략**한다.

```java
DungeonWallsTilemap.skipCells.add(cell);   // 북쪽 N칸
GameScene.updateMap(cell);                 // 해당 칸 타일맵 갱신
```

- 북쪽 벽에 안 잘림 ✅ / 남쪽 벽의 하단 가림 유지 ✅ / 레이어 순서 무변경 ✅
- 트레이드오프: 머리 위치의 벽이 잠시 보이지 않는다 (SPD 자체 보스도 동일)

**구현**: `OperatorSprite.updateWallSkip()` — 위치·가시성 변화 시에만 갱신하며,
`die()` / `destroy()`에서 정리한다. 생략 범위는 `WALL_SKIP_ROWS`(기본 2칸 = 실제 몸체 약 32px) 상수로 조절.

> 대형 몹(로댄 등)에 전용 스프라이트를 붙일 때도 같은 패턴을 적용하면
> 잘림 없이 큰 스프라이트를 쓸 수 있다.

## 3. 프레임 규격 (표준)

| 항목 | 값 | 비고 |
|------|-----|------|
| 캔버스 | **64×64** | 추후 모션/이펙트가 32×32 타일 영역을 벗어날 것을 대비 |
| 정렬 | 횡 중앙 / 종 하단 | 캔버스 중앙하단에 발을 맞춤 |
| 단일 프레임 시트 | `{이름}_Standing.png` | 64×64 1프레임 |
| 풀 애니메이션 시트(추후) | `{이름}.png` | 프레임 가로 나열 (예: 256×64 = 4프레임) |

### 정렬이 자동으로 맞는 원리

`CharSprite.worldToCamera()`는 프레임을 타일에 배치할 때:
- **횡**: `width()*0.5`만큼 좌측 이동 → 캔버스 가로 중앙이 타일 중앙에 정렬
- **종**: 캔버스 하단이 타일 바닥에 닿고 `perspectiveRaise`(6px)만큼 들어 올림

→ 캔버스 중앙하단에 발을 그리면 **코드 오프셋 보정 없이** 타일 위에 자연스럽게 선다.
   (64×64는 16×16 타일의 4배라 캐릭터가 타일을 크게 넘어서는 것은 정상)

## 4. 에셋 ↔ 오퍼레이터 연결

### Assets 경로 (`Assets.Operators`)

```java
public static final String ENDMINISTRATOR_SPRITE = "sprites/Endmistrator_Standing.png";
public static final String JINCHEONWOO_SPRITE    = "sprites/Chen_Standing.png";
public static final String FELIKA_SPRITE         = "sprites/Perlica_Standing.png";
```

### Operator.spriteSheet()

```java
// Operator.java — 기본 null (스프라이트 미제작 오퍼레이터)
public String spriteSheet() { return null; }
```

각 오퍼레이터에서 오버라이드:

```java
// Endministrator.java
@Override public String spriteSheet() { return Assets.Operators.ENDMINISTRATOR_SPRITE; }
```

### GameScene 분기

```java
// GameScene.java — 메인 오퍼레이터 스프라이트 존재 시 OperatorSprite 사용
if (Dungeon.hero.activeMainOperator != null
        && Dungeon.hero.activeMainOperator.spriteSheet() != null) {
    hero = new OperatorSprite();
} else {
    hero = new HeroSprite();   // 폴백 (기존 SPD 스프라이트)
}
```

## 5-B. 선택 화면 일러스트(스플래시 아트) 규격

> 인게임 스탠딩 스프라이트(64×64)와 **별개 에셋**이다.
> 경로: `operators/illustrations/<name>.png` → `Operator.illustration()`

### 표시 방식 (fill + crop)

일러스트 영역은 **가로 전체 × (높이 − 76)** 으로, 종횡비가 약 **2.9 : 1 (넓고 낮음)** 이다.

| 상황 | 카메라(게임유닛) | 일러스트 영역 |
|------|-----------------|--------------|
| 가로 최소 | 240×160 | 240×84 |
| 대형 UI | 360×200 | 360×124 |
| 데스크톱(예) | 480×250 | 480×174 |

전신 스플래시 아트는 보통 **≈1:1 세로 구도**라 fit(축소)으로 넣으면 좌우 여백이 60%가
넘고 축소율도 커져 디테일이 뭉개진다. 따라서 **fill+crop**(영역을 꽉 채우고 넘치는
세로를 잘라냄)을 사용하며, 잘린 뒤 **어느 구간을 보여줄지**는 오퍼레이터별로 지정한다.

```java
// Operator.java — 기본 0.25 (얼굴이 상단 1/3에 있는 전신 아트 기준)
public float illustrationAnchorY() { return 0.25f; }

// 아트 구도에 맞춰 각 오퍼레이터에서 오버라이드
@Override public float illustrationAnchorY() { return 0.18f; }
```

`anchorY` : `0.0` = 이미지 최상단 노출 / `0.5` = 중앙 / `1.0` = 최하단

### 화질 (LINEAR 필터)

SPD 텍스처 기본값은 `NEAREST`라, 비정수 배율 축소 시 픽셀이 지글거린다.
일러스트에는 **`Texture.LINEAR`** 를 적용해 부드럽게 축소한다 (`OperatorSelectScene`에서 처리).

### 아트 제작 가이드

| 항목 | 권장 |
|------|------|
| 캔버스 | 가로 **720~1000px** (그 이상은 축소만 심해져 이득 없음) |
| 배경 | **투명 PNG** (흰 배경이면 어두운 UI에 흰 사각형이 뜸) |
| 여백 | 바깥 빈 공간은 **트림** — 같은 배율에서 캐릭터가 더 크게 보임 |
| 구도 | **얼굴·상체를 위쪽 1/3 안에** 배치 (크롭이 쉬워짐) |
| 하단 | 하단 25%(최대 60유닛)에 **어두운 페이드**가 덮임 → 다리/배경 등 어두워도 무해한 영역으로 |
| 좌우 | 화면 폭에 따라 잘릴 수 있으니 **중요 요소는 가로 중앙 쪽에** |
